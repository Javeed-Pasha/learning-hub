Module 0

dbt is the T in ELT, and in 2026 it runs on two engines

About 45 minutes of reading. No setup yet.

dbt does one job: it turns SELECT statements you write into tables and views inside the warehouse, in the right order, with tests and documentation attached. You write a model as a select; dbt compiles the Jinja in it to plain SQL, works out the dependency order from ref() calls, then runs the CREATE TABLE, CREATE VIEW or MERGE statements for you.

It does not extract or load. Data arrives in BigQuery through Fivetran, Airbyte, Datastream, Dataflow, custom Python or a GCS load job. dbt starts once raw tables exist, and the warehouse does all the compute. Nothing flows through a dbt server the way rows flow through the PowerCenter Integration Service.

Why clients pay for it

  • Version control. Every transformation is a text file in Git, reviewed in a pull request.
  • Tests on every build. Uniqueness, nulls, referential integrity and business rules run with the models, not in a separate tool.
  • Lineage and docs for free. The dependency graph and documentation site are generated from the code, so they never go stale.
  • Environments. The same code builds into a developer dataset, a CI dataset and production by switching a target.

Self-check

Does dbt copy data from Salesforce into BigQuery?

No. An ingestion tool (Fivetran, Airbyte, a custom job) loads raw Salesforce tables. dbt only transforms what is already in the warehouse.

A client is on dbt 1.9 in dbt platform. What should you raise early?

1.9 is out of support. Ask whether moving to a current release track or to v2 is in scope, because deprecated syntax will start failing and an upgrade changes how long everything else takes.

What is the practical difference between v2 and v1 for daily work?

v2 parses and compiles much faster and catches SQL errors locally without running them, and the VS Code extension needs it. v1 only finds SQL errors when the warehouse runs the query, and supports many more adapters.

Module 2

Git is how every dbt change reaches production

About 2.5 hours with the lab. Every later module assumes this workflow.

In PowerCenter a change moved through folders and deployment groups. In dbt, it moves through Git: a branch holds your change, a pull request is the review, CI is the test run, and merging to main is the deployment. Clients judge you on this workflow before they ever read your SQL.

A branch is just a movable pointer to a commit. main always equals production and is protected: nobody pushes to it directly.

One-time setup

The daily loop

Conventions clients recognise

  • Branch names: feat/…, fix/…, chore/…, docs/….
  • Commit messages (Conventional Commits): feat(staging): add stg_thelook__events, fix(marts): dedupe order items before join, test: add unit test for delivery days, ci: cache dbt packages.
  • Small pull requests: one model or one concern each, with a description of what, why, how tested and impact.
  • Squash merge into main, so each pull request is one revertable commit, and history stays linear.

Staying current: fetch, pull, rebase

fetch only downloads; pull downloads and updates your branch. Rebase your own feature branch to keep it current; never rebase a branch someone else works on, and never force-push main.

Resolving a conflict

YAML files are where dbt teams collide most, because two people add tests to the same file.

Protecting main and releasing

  • In GitHub, Settings, Rules (or Branches): require a pull request, require status checks (your CI job, from module 13), require linear history, block force pushes and deletions.
  • CODEOWNERS makes the right reviewer automatic. On client projects it is usually their lead.
  • Tag releases so you can say exactly what is in production: git tag -a v1.2.0 -m "Add returns mart", then git push origin v1.2.0, and write release notes in GitHub.
  • Hotfix: branch from main, fix, fast review, merge; CD deploys it. If it makes things worse, revert the merge commit.

Branching strategy

Use trunk-based development: short-lived branches off main, merged within a day or two. Some enterprises run GitFlow (develop, release/* branches) and map each branch to an environment; dbt platform environments can follow either. On GitLab a pull request is a "merge request"; on Azure DevOps the review and pipeline ideas are the same.

Secrets and Git

Never commit keys, passwords, profiles.yml with credentials, or client data. If a secret is ever pushed, rotate it immediately; rewriting history does not un-leak it. The gitleaks pre-commit hook in module 3 blocks most accidents.

Informatica lens

Check-in and check-out become commit and push; a deployment group becomes a pull request; labels become tags; "who changed this mapping" becomes git log -p path or git blame, with the reason in the message.

Self-check

What is the difference between git fetch and git pull?

fetch downloads remote commits and updates remote-tracking branches without touching your files. pull is fetch plus integrating those commits into your current branch (a fast-forward with pull.ff only).

A merged pull request broke production. Revert or reset?

Revert. It adds a new commit that undoes the change, goes through review and CI, and keeps shared history intact. Reset rewrites history and breaks everyone else's clones.

Why squash-merge dbt pull requests?

Each change becomes one commit on main, which makes history readable, releases easy to describe, and a bad change revertable in one step.

Module 3

Set up every project the way production runs it

About 4 to 6 hours across the three tracks. Do DuckDB first, BigQuery in week 2, Snowflake in week 6.

Amateur projects start with one login, one schema and a laptop that builds production. Professional ones separate environments, people and machines from day one. Set the course project up the professional way, and every client setup later will feel familiar.

Seven rules every setup in this course follows

  1. Three environments. dev (yours), ci (one per pull request, thrown away), prod (built only by automation).
  2. People and machines are different identities. You log in as yourself in dev; CI and production use service identities.
  3. Least privilege. The transformer can read raw data and write analytics data, nothing more. Reporting tools only read marts.
  4. No secrets in Git. Profiles read credentials from environment variables; CI reads them from secrets or keyless federation.
  5. Everything through pull requests. main is protected; CI must pass.
  6. Pinned versions. dbt, adapters and packages are pinned, so a build today equals a build next month.
  7. Raw is read-only to dbt. A loader writes raw data; dbt only reads it.

Self-check

Why should your laptop never build production?

Production must be reproducible and audited: built from main, by a service identity, with logs. A laptop build uses your personal credentials, uncommitted code and whatever versions you happen to have installed.

What does Workload Identity Federation remove from your CI?

Long-lived JSON keys. GitHub proves the workflow's identity with a short-lived OIDC token, and Google exchanges it for temporary credentials, limited to your repository by the attribute condition.

Why three Snowflake roles instead of one?

Each tool gets only what it needs: the loader writes raw, dbt reads raw and writes analytics, BI tools read analytics. A leaked BI credential cannot change data, and a bad dbt change cannot damage raw.

Module 4

A dbt project is folders, YAML and SELECT statements

About 60 minutes.

The + prefix marks a config that applies to every model in that folder. The most specific setting wins: a config() block inside a model beats its YAML properties file, which beats dbt_project.yml.

ref() and source() are the whole trick

At compile time ref() becomes the fully qualified table for the current target: `jp-dbt-lab`.`dbt_jp_staging`.`stg_thelook__orders` on BigQuery, analytics_dev.dbt_jp_staging.stg_thelook__orders on Snowflake, "dev"."dbt_jp_staging"."stg_thelook__orders" on DuckDB. It also records the dependency, which is how dbt knows the build order and draws lineage. Never hard-code a table name that dbt builds.

The build loop

CommandWhat it does

dbt compileRenders Jinja to SQL in target/compiled/. Read this when something looks wrong.

Selecting nodes

--select (or -s) is the only selector flag to use. The old --models and -m warn in v1.10 and fail in v2, so replace them when you see them in a client repo.

House style reviewers expect

  • Lower-case SQL, trailing commas, four-space indents, one column per line.
  • Every model opens with "import" CTEs (with orders as (select * from {{ ref('…') }})), then logic CTEs, then a final select * from final.
  • Prefixes: stg_, int_, fct_, dim_; double underscore between source and entity.
  • Primary key first; booleans start is_ or has_; timestamps end _at, dates end _date.
  • One YAML file per folder: _thelook__sources.yml, _thelook__models.yml, _marts__models.yml.
  • No hard-coded database or schema names anywhere; only ref(), source() and target.

SQLFluff (module 3) enforces most of this automatically, so reviews can focus on logic.

Engine notes

DuckDB
Lower-case identifiers; the database name is the file name (dev for dev.duckdb).
BigQuery
Project, dataset, table. Names are case-sensitive, so stay lower-case.

Self-check

What is the difference between dbt run and dbt build?

run only builds models. build also seeds, snapshots and tests, in DAG order, and skips models whose upstream tests failed, so bad data stops spreading.

Where do you look to see the exact SQL that hit BigQuery?

target/run/ for the full statement including DDL or MERGE; target/compiled/ for the rendered select; logs/dbt.log for everything with timings.

Module 5

Staging models are your clean, one-to-one contract with raw data

About 2 hours with the lab. You will build seven models.

Declare the sources

DBT_RAW_DATABASE lets one YAML file find raw data on every engine: leave it unset on DuckDB and BigQuery (raw lives in the same file or project), set it to RAW on Snowflake. From v1.10, freshness, meta, tags, docs, group and access belong under config:. Older repos put them at the top level and now get deprecation warnings.

One staging model per source table

Staging rules: rename to your conventions, cast types, light cleanup (trim, lower-case codes), and nothing else. No joins, no aggregations. Materialize as views. Name them stg_<source>__<entity>. Check real column names first with dbt show --inline "select * from {{ source('thelook','orders') }} limit 5".

Seeds for small reference data

Run dbt seed. Seeds are for small, slowly changing lists that analysts own, such as mappings and code descriptions. They are not a loading tool. The list above is deliberately incomplete: the relationships test you add in module 7 will tell you which countries are missing.

Informatica lens

Staging is the Source Qualifier plus the rename-and-cast Expression you put at the front of every mapping, done once per table and reused everywhere. It is the same bronze-to-silver step you have built in Oracle, without the procedure.

Lab

  1. Write the sources file and staging models for all seven tables: orders, order_items, products, users, events, inventory_items, distribution_centers.
  2. Add the seed and run dbt seed.
  3. Run dbt build -s staging, then dbt freshness (on 1.12, dbt source freshness). Your raw copy is a one-time load, so freshness turns to a warning within days: exactly the alert a client gets when a loader stops.
  4. Branch, commit feat(staging): add thelook staging layer, open a pull request, merge.

Engine notes

DuckDB
Raw tables sit in schema thelook inside each .duckdb file, loaded by scripts/load_raw_duckdb.py.
BigQuery
Raw is the thelook dataset in your project. Freshness can also use table metadata when there is no loaded_at_field.
Snowflake
Raw is RAW.THELOOK. Casting to plain numeric gives NUMBER(38,0) and silently drops decimals; dbt.type_numeric() gives a scale and avoids that trap.

Self-check

Why not join users onto orders in staging?

Staging is a one-to-one, reusable cleanup of each source. Joins belong in intermediate or mart models, so every downstream model starts from the same clean pieces and the grain of staging never changes.

When is a seed the wrong tool?

For large data, frequently changing data or anything a system produces. Load those with an ingestion tool and declare them as sources.

Self-check

When is a view the wrong choice for a mart?

When the logic is heavy and a dashboard queries it often. Every refresh re-runs the joins and scans the base tables. Materialize it as a table or incremental model instead.

Why might a client dislike lots of ephemeral models?

They do not exist in the warehouse, so nobody can query them to debug, and deep chains of them produce very long compiled SQL.

Unit tests check logic, not data

Columns you leave out of given are null, and expect only compares the columns you list. Run unit tests in development and CI, not in production: dbt test -s "test_type:unit".

Contracts lock a model's shape

With a contract, every column must be listed with its type, and the build fails before it replaces the table if the SQL drifts. Use it on marts that dashboards or other teams depend on.

Write your own generic test

A generic test is just a query that returns the failing rows, with model and column_name filled in by dbt. Once you can write these, any client rule ("no future dates", "totals reconcile") becomes reusable in one line of YAML.

Informatica lens

These replace the reconciliation queries you used to run by hand after a load, and they run on every build. dbt test --store-failures writes failing rows to an audit dataset, much like a reject file.

Self-check

Unit test or data test: which one catches a wrong CASE statement?

A unit test. It feeds known inputs through the logic and compares the outputs. Data tests check properties of real data, which may never contain the edge case.

How do you stop a noisy test from failing the whole production build?

Rules that save you from production incidents

  • Duplicates kill MERGE. BigQuery's "UPDATE/MERGE must match at most one source row for each target row" and Snowflake's "Duplicate row detected during DML action" both mean the batch has repeated keys. Deduplicate with row_number() as above.
  • Schema changes. The default on_schema_change is ignore, so a new column silently never appears. Use append_new_columns or sync_all_columns, or plan a full refresh.

Snapshots give you SCD Type 2 history in a dozen lines

Each time dbt snapshot runs, dbt compares the current source rows with the snapshot table. Changed rows get their dbt_valid_to closed and a new version is inserted. dbt adds dbt_scd_id, dbt_updated_at, dbt_valid_from and dbt_valid_to.

  • timestamp strategy: use when the source has a reliable updated_at.
  • check strategy: compares check_cols (a list, or all) when there is no trustworthy timestamp. It costs more because it compares column values.
  • hard_deletes: ignore (default), invalidate (close the record) or new_record (add a row flagged deleted).
  • dbt_valid_to_current: a far-future date for current rows instead of null, which makes range joins simpler.

1. Write, audit, publish

A normal dbt build replaces tables as it goes, so if a test fails halfway, dashboards can see a mix of old and new data. Write-audit-publish builds everything somewhere private, tests it, and only then switches consumers over in one step.

On BigQuery there is no schema swap. The common pattern is to build into an audit dataset, test, then copy tested tables over the production ones with dbt clone or table copy jobs. On any engine, the cheaper first step is simply dbt build, which already stops downstream models when an upstream test fails.

2. Model versions for breaking changes

When a public mart must change shape (a column renamed or dropped), publish a new version beside the old one and give consumers a deadline.

Interview and screening practice

Answer these out loud before your first client call

Say each answer in under a minute, then open it to compare.

What is the difference between ref() and source()?

source() points to raw tables loaded by something else and declared in YAML. ref() points to models dbt builds. Both resolve to the right relation for the target and create lineage edges.

Explain the materializations and when you use each.

Views for staging and light logic, tables for marts BI reads often, incremental for large growing facts, ephemeral for small reusable steps, materialized views for simple aggregates that must stay fresh.

How does an incremental model work, and what can go wrong?

First run builds everything; later runs filter with is_incremental() and merge into {{ this }}. Risks: duplicate keys breaking MERGE, late data missed without a lookback, schema changes ignored, and full-table scans on MERGE.

merge, insert_overwrite or microbatch on BigQuery?

Merge for rows that change after arrival. Insert_overwrite for large partitioned facts recomputed a partition at a time. Microbatch for time-series data where you want batch-level backfills and retries.

How do you implement SCD Type 2?

A snapshot with timestamp or check strategy, then a dimension built from it with valid-from and valid-to, joined to facts on the key and a date range.

What tests do you put on a new model?

Unique and not null on the grain, relationships to dimensions, accepted values on status codes, a unit test for any tricky logic, and a contract if others depend on it.

Unit test versus data test?

A unit test checks logic with mocked inputs and runs in dev and CI. A data test checks properties of real data on every build.

How do you run only what changed in CI?

dbt build --select state:modified+ --defer --state prod-artifacts against a per-PR dataset.

Why do models land in dbt_x_marts instead of marts?

Default generate_schema_name concatenates target schema and custom schema. Override it so prod uses the custom name alone.

What is the difference between dbt run and dbt build?

build runs seeds, snapshots, models and tests in DAG order and skips children of failed tests.

How would you deduplicate a source with repeated events?

In staging or the incremental model: qualify row_number() over (partition by event_id order by loaded_at desc) = 1, plus a unique test to prove it.

How do you reduce BigQuery cost for a dbt project?

Partition and cluster marts, incremental for big facts, partition filters, avoid heavy views under dashboards, cap bytes billed, slim CI with defer, and find the costliest models in the jobs history.

What is a macro, and when would you write one?

A reusable Jinja function that returns SQL. Write one when the same expression or pattern appears in three or more places, or to override dbt behaviour such as schema naming.

What is the difference between dbt v1 and v2?

v2 is the Rust engine (formerly Fusion), GA since September 2026: faster parsing, local SQL compilation and static analysis, bundled adapters. v1 is the Python engine, still supported, with many more adapters.

How do you migrate an Informatica mapping to dbt?

Inventory and classify, design the layers, rebuild in a vertical slice with tests, reconcile against the legacy target with audit_helper, run in parallel, then cut over.

A dashboard shows wrong revenue after your change. What do you do?

Check the PR diff and lineage for affected models, compare the model before and after with audit_helper or a sum by day, look for fan-out from a new join, fix, add a test that would have caught it.

What do exposures give you?

Dashboards in the lineage graph, impact analysis, and the ability to build and test everything one dashboard depends on.

When would you not use dbt?

For extraction and loading, streaming with second-level latency, or heavy non-SQL processing better suited to Spark or Python services.

git fetch versus git pull?

Fetch downloads remote commits without changing your files; pull fetches and then integrates them into your current branch.

A merged change broke production. What do you do in Git?

Open a pull request with git revert of the merge commit, let CI pass, merge; CD redeploys. Never reset or force-push main.

Walk me through your dbt CI/CD.

Pull requests run lint and a slim build of changed models into a per-PR schema, deferring to production; merges to main run the production build with a service identity, keep the manifest and publish docs; full refreshes need an approval.

How do you keep credentials out of a dbt project?

Profiles read environment variables; CI uses keyless federation on GCP and key pairs stored as secrets on Snowflake; pre-commit runs gitleaks; humans and machines use separate identities.

How would you set up Snowflake for dbt?

Separate RAW and ANALYTICS databases, loader, transformer and reporter roles, one XS warehouse per workload with short auto-suspend, a service user with key-pair auth, and future grants so new tables are readable by reporting.

What changes when moving a dbt project from BigQuery to Snowflake?

Profiles and auth, engine-specific configs (partitioning becomes nothing or clustering), dialect functions (handled by cross-database macros and dispatch), type names in contracts, identifier case, and cost levers (bytes versus warehouse seconds).

What is write-audit-publish?

Build into a private location, run tests, then expose the results in one step (a schema swap or clone), so consumers never see partly built or failing data.
