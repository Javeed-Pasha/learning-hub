This page turns the architecture story into a concrete build pattern. The example is a certified daily sales data product that ingests ERP, CRM, and e-commerce data, standardizes it, applies business rules, publishes curated outputs, and surfaces operational controls needed for production support.

In this reference pattern, bronze, silver, and gold are implemented as Apache Iceberg tables in the data lakehouse so the platform can support schema evolution, partition-aware processing, snapshot-based recovery, and consistent table management across all layers.

The notebook walkthrough is still useful as a learning aid, but the actual metadata-driven runtime in this repo now lives in spark/runtime_framework.py, spark/run_pipeline.py, spark/replay_runner.py, and ddl/demo_metadata_framework.sql.

Lakehouse and Medallion Are Related, Not Identical

ConceptWhat It Means Here
LakehouseThe broader platform style combining scalable data storage, transformation, governance, and analytics-oriented consumption on one managed foundation.
Medallion architectureThe data-layering pattern inside that platform, where bronze captures landed source state, silver standardizes and derives reusable structures, and gold publishes curated outputs.
💡

Simple distinction: lakehouse describes the overall platform architecture, while medallion describes the refinement path of the data inside that architecture. In this page, the implementation uses a lakehouse-style platform with medallion-style layers.

Reusable Ingestion Pattern Matrix

load_modeHow the Same Framework Behaves
FULLTruncates or snapshots target state according to source configuration and reloads the entire source set.
INCREMENTAL_TSUses configured watermark columns and appends each changed extracted version into bronze Iceberg tables.
CDCReads ordered change events, preserves operation type and sequence metadata, and derives current/history in silver Iceberg tables.
FILEValidates file naming, schema, and checksum rules before landing data into bronze Iceberg tables and starting standardization.
EVENTUses checkpointing and event offsets while preserving replayability by partition or event window.

What Iceberg Does and Does Not Do

ConcernIceberg Helps WithIceberg Does Not Replace
CDC handlingEfficient storage of landed change data, merge operations, snapshot history, and table-level recovery behavior.Source-side CDC capture. If the source does not emit ordered change events, Iceberg does not invent them for you.
Location change examplePreserving both extracted versions, such as London and later Bangalore, when the bronze landing appends each extract into Iceberg.Guaranteeing every intermediate source event unless the upstream extraction pattern is true CDC.
ReplaySnapshot-aware restore options, table versioning semantics, and governed overwrite or merge behavior.The need for a defined replay design based on preserved bronze inputs, business keys, and ordering metadata.

def run_pipeline_for_source(
    spark,
    source_name,
    catalog='demo',
    forced_batch_id=None,
    requested_by='runtime',
):
    config = get_source_registration(spark, source_name, catalog)
    batch_id = create_batch_run(
        spark,
        source_name,
        f'PIPELINE_{config.load_mode}',
        requested_by,
        catalog,
        forced_batch_id=forced_batch_id,
    )

    upper_bound = resolve_upper_bound(spark, config)
    source_df = build_extract_df(
        spark,
        config,
        config.last_successful_watermark,
        upper_bound,
    )

        spark,

Bronze Load Script Example

def append_bronze(spark, extract_df, config, batch_id, run_mode):
    bronze_df = (
      extract_df
      .withColumn("pipeline_batch_id", F.lit(batch_id))
      .withColumn("bronze_load_ts", F.current_timestamp())
      .withColumn("source_name", F.lit(config.source_name))
      .withColumn("load_mode", F.lit(run_mode))
      .withColumn("record_hash", F.sha2(F.to_json(F.struct(*extract_df.columns)), 256))
    )

    bronze_df.writeTo(config.bronze_table).append()

Silver Build Script Example

def build_scd2_frames(bronze_df, config):
    current_window = Window.partitionBy(*config.primary_keys).orderBy(
        F.col(config.ordering_column).desc_nulls_last(),
        F.col('bronze_load_ts').desc_nulls_last(),
    )
    history_window = Window.partitionBy(*config.primary_keys).orderBy(
        F.col(config.ordering_column).asc_nulls_last(),
        F.col('bronze_load_ts').asc_nulls_last(),
    )

    ranked_df = (
        bronze_df
        .withColumn('_row_rank', F.row_number().over(current_window))
        .withColumn('_next_effective_from', F.lead(F.col(config.ordering_column)).over(history_window))
    )

    history_df = ranked_df.select(
        'customer_id',
        'location',
        'source_change_ts',
        F.col(config.ordering_column).alias('effective_from'),
        F.col('_next_effective_from').alias('effective_to'),
        (F.col('_row_rank') == 1).alias('is_current'),
        'pipeline_batch_id',
        'bronze_load_ts',
        'record_hash',
    )
    current_df = history_df.where(F.col('is_current') == True)

Gold Publish Script Example

def publish_current_snapshot(spark, config, current_df):

Timestamp-Based Incremental Load vs True CDC

Many enterprise systems do not expose log-based CDC. In those cases, teams often use timestamp-based incremental extraction. That pattern works, but it should be described accurately: it captures changed source state over time, not necessarily every source change event.

SELECT *
FROM source_customer
WHERE COALESCE(update_ts, insert_ts) > watermark;
PatternWhat You GetMain Limitation
True CDCOrdered insert, update, and delete events with sequence metadata.Usually needs source-log access or a CDC-capable platform.
Timestamp incrementalThe latest changed row as seen at extract time.May miss intermediate changes and often misses hard deletes unless handled separately.

Bronze behavior

Even with timestamp-based extraction, bronze Iceberg tables should append each extracted version with load metadata rather than overwriting prior landed records. That preserves replayability and snapshot-based recovery.

Silver behavior

Silver Iceberg current and history tables are then rebuilt by ordering the extracted versions using source change timestamp plus landing metadata such as batch ID or extract time.

⚠

Important distinction: if customer 1 was extracted once with London and later with Bangalore, Iceberg can preserve both landed states in bronze. That is useful extracted-state history, but it is not automatically the same as source CDC unless the upstream source delivered ordered change events.

How Silver Current and Silver History Are Derived

WITH ranked AS (
    SELECT
        customer_id,
        location,
        source_change_ts,
        bronze_load_ts,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY source_change_ts DESC, bronze_load_ts DESC
        ) AS rn,
        LEAD(source_change_ts) OVER (
            PARTITION BY customer_id
            ORDER BY source_change_ts, bronze_load_ts
        ) AS next_change_ts
    FROM bronze_customer_incremental
)
SELECT * FROM ranked;
Silver OutputHow It Uses Ranked Bronze Rows
silver_customer_currentKeeps only rows where rn = 1, then writes the result into an Iceberg current table using repeatable merge or replace logic.
silver_customer_historyUses source_change_ts as effective_from, next_change_ts as effective_to, and flags the last row as is_current = true in a history-oriented Iceberg table.

How Silver Rebuild Works If Silver Is Corrupted or Deleted

Recovery OptionWhen to Use ItHow It Works
Snapshot restoreFast recovery from a recent accidental delete, bad write, or corruption event where the required Iceberg metadata and snapshots are still available.Restore the affected silver Iceberg table to a known good snapshot or table version.
Authoritative rebuild from bronzePreferred recovery path when silver logic must be rerun cleanly or when you want deterministic reconstruction of current and history tables.Read preserved bronze Iceberg inputs, reapply ordering and transformation rules, then recreate silver_customer_current and silver_customer_history.

The important design point is that Iceberg improves restore and table management, but the durable business rebuild strategy still depends on preserved bronze history plus deterministic silver logic.

Authoritative Rebuild Flow for Silver Current and Silver History

1. Read bronze_customer_incremental_iceberg for the required scope
2. Order records by business key, source_change_ts, and bronze_load_ts
3. Recompute ranked rows and effective date boundaries
4. Recreate silver_customer_history_iceberg from the ordered result
5. Recreate silver_customer_current_iceberg using rows where rn = 1
6. Re-run quality checks and publish only after validation passes

Example Rebuild Logic

CREATE OR REPLACE TABLE silver.customer_history_iceberg AS
WITH ranked AS (
    SELECT
        customer_id,
        location,
        source_change_ts,
        bronze_load_ts,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY source_change_ts DESC, bronze_load_ts DESC
        ) AS rn,
        LEAD(source_change_ts) OVER (
            PARTITION BY customer_id
            ORDER BY source_change_ts, bronze_load_ts
        ) AS next_change_ts
    FROM bronze.customer_incremental_iceberg
)
SELECT
    customer_id,
    location,
    source_change_ts AS effective_from,
    next_change_ts AS effective_to,
    CASE WHEN rn = 1 THEN true ELSE false END AS is_current,
    bronze_load_ts
FROM ranked;

CREATE OR REPLACE TABLE silver.customer_current_iceberg AS
SELECT customer_id, location, effective_from AS source_change_ts, bronze_load_ts
FROM silver.customer_history_iceberg
WHERE is_current = true;

Replay Modes

Replay ModeWhen It AppliesWhat It Actually Does
Normal incremental continuationRoutine scheduled execution after the last successful batch.Reads only new source data or bronze ranges newer than the recorded watermark.
Iceberg snapshot restoreA recent bad write, accidental delete, or corruption event affected a silver table and the required snapshot still exists.Restores the damaged Iceberg table to a known good table snapshot without recomputing all logic.
Date-range logical replayA limited time window in silver must be recomputed due to bad source data, incorrect logic, or repair needs.Reprocesses preserved bronze rows for the selected start and end timestamps, then rewrites the affected silver outputs.
Entity-specific logical replayOnly a subset of business keys such as specific customers or products must be repaired.Filters bronze inputs by entity scope and recomputes only the relevant current and history outputs.
Full logical rebuildSilver must be reconstructed from scratch or a deterministic re-creation is required.Re-reads all preserved bronze inputs and rebuilds silver current and silver history from first principles.

Replay Runner Script Example

def run_replay(spark, replay_request_id):
    request = spark.sql(f"""
      SELECT *
      FROM ctl.replay_request
      WHERE replay_request_id = {replay_request_id}
    """).first()

    if request.replay_mode == 'ICEBERG_RESTORE':
      restore_iceberg_snapshot(
        table_name='silver.customer_current_iceberg',
        snapshot_id=request.entity_filter
      )
      return

    if request.replay_mode == 'DATE_RANGE':
      bronze_df = spark.table('bronze.customer_incremental_iceberg') \
        .where((F.col('source_change_ts') >= request.start_ts) &
             (F.col('source_change_ts') < request.end_ts))
    elif request.replay_mode == 'ENTITY':
      bronze_df = spark.table('bronze.customer_incremental_iceberg') \
        .where(F.expr(request.entity_filter))
    elif request.replay_mode == 'FULL_REBUILD':
      bronze_df = spark.table('bronze.customer_incremental_iceberg')
    else:
      raise ValueError(f"Unsupported replay mode: {request.replay_mode}")

    rebuild_silver_from_bronze(spark, bronze_df)
💡

Precision point: snapshot restore is a physical recovery option for Iceberg tables. Date-range, entity, and full rebuild modes are logical reprocessing strategies driven by preserved bronze history.
