What is Apache Spark?

⏱ 5 min📌 Module 01🎓 Theory

Apache Spark is a unified analytics engine for large-scale data processing. It provides high-level APIs in Python (PySpark), Scala, Java, and R, and supports batch processing, streaming, machine learning, and graph processing.

Why Spark?

100x Faster than MapReduce

In-memory processing. Avoids disk I/O between stages. The DAG optimizer plans execution efficiently.

Unified Engine

Batch, streaming, ML, and SQL — all in one framework. No need for separate tools.

Lazy Evaluation

Transformations are not executed immediately. Spark builds an optimized plan and executes only when an action is called.

Scalable

Scales from a laptop to thousands of nodes. Runs on YARN, Mesos, Kubernetes, or standalone.

Spark vs Hadoop MapReduce

AspectMapReduceApache Spark
ProcessingDisk-based (read/write HDFS per stage)In-memory (100x faster)
Ease of UseVerbose Java codeHigh-level APIs (PySpark, Scala)
StreamingNot nativeStructured Streaming built-in
MLSeparate (Mahout)MLlib built-in
DAG2-stage only (Map → Reduce)Multi-stage DAG optimizer
Fault ToleranceData replicationRDD lineage (recompute lost partitions)

Key Concepts

Driver

Runs your main program. Creates the SparkSession, builds the DAG, distributes tasks to executors.

Executor

JVM process on a worker node. Runs tasks assigned by the driver. Stores cached data in memory.

Job → Stage → Task

Job: triggered by an action. Stage: set of tasks separated by shuffles. Task: unit of work on one partition.

DAG (Directed Acyclic Graph)

Spark builds a DAG of transformations and optimizes it before execution. Stages are created at shuffle boundaries.

Execution Flow

  Your Code
      │
      ▼
  Logical Plan → Catalyst Optimizer → Physical Plan
      │
      ▼
  DAG Scheduler → splits into Stages (at shuffle boundaries)
      │
      ▼
  Task Scheduler → assigns Tasks to Executors
      │
      ▼
  Executors → run tasks on partitions → return results

RDDs, DataFrames & Datasets

⏱ 4 min📌 Module 03🎓 Core Concepts

Evolution of Spark APIs

APIType SafetyOptimizationUse Case
RDD (Spark 1.0)Compile-timeNone — manual optimizationLow-level control, unstructured data
DataFrame (Spark 1.3)Runtime onlyCatalyst + TungstenStructured data, SQL-like operations
Dataset (Spark 1.6)Compile-timeCatalyst + TungstenType-safe structured data (Scala/Java only)
🔥

In PySpark, DataFrame is the primary API. Datasets are not available in Python. RDDs are used only for very low-level operations. 95% of your work will use DataFrames.

Transformations vs Actions

Transformations (Lazy)

Return a new DataFrame. Not executed until an action triggers them.
select, filter, groupBy, join, withColumn, orderBy

Actions (Eager)

Trigger execution and return results.
show(), count(), collect(), write, take(), first()

Narrow vs Wide Transformations

TypeShuffle?ExamplesImpact
NarrowNomap, filter, select, withColumnFast — data stays on same partition
WideYesgroupBy, join, orderBy, distinct, repartitionExpensive — data moves across network

Basic Operations

from pyspark.sql import functions as F

# Schema & preview
df.printSchema()
df.show(5)
df.count()
df.columns
df.describe().show()

df.select("name", "age", "salary")

# Add / Modify columns
df.withColumn("annual_salary", F.col("salary") * 12)
df.withColumn("name_upper", F.upper(F.col("name")))
df.withColumnRenamed("name", "full_name")

# Drop columns / duplicates
df.drop("temp_col")
df.dropDuplicates(["email"])

Aggregations

# Group by + aggregate
df.groupBy("department").agg(
    F.count("*").alias("headcount"),
    F.avg("salary").alias("avg_salary"),
    F.max("salary").alias("max_salary"),
    F.sum("salary").alias("total_salary")
).orderBy(F.desc("avg_salary")).show()

# Multiple groupBy columns
df.groupBy("department", "location").count().show()

Window Functions

from pyspark.sql.window import Window

# Rank employees by salary within each department

df.withColumn("rank", F.dense_rank().over(window_spec)) \
  .withColumn("row_num", F.row_number().over(window_spec)) \
  .withColumn("running_total", F.sum("salary").over(window_spec)) \
  .show()

Spark SQL

⏱ 4 min📌 Module 07🎓 Hands-On

Spark SQL lets you use standard SQL queries on DataFrames. Register a DataFrame as a temp view, then query it.

Temp Views & SQL Queries

# Register DataFrame as a SQL temp view
df.createOrReplaceTempView("employees")

# Run SQL queries
result = spark.sql("""
    SELECT department,
           COUNT(*) AS headcount,
           AVG(salary) AS avg_salary,
           MAX(salary) AS max_salary
    FROM employees
    WHERE status = 'active'
    GROUP BY department
    HAVING COUNT(*) > 5
    ORDER BY avg_salary DESC
""")

result.show()

SQL vs DataFrame API — Same Result

# DataFrame API
df.filter(F.col("status") == "active") \
  .groupBy("department") \
  .agg(
      F.count("*").alias("headcount"),
      F.avg("salary").alias("avg_salary")
  ) \
  .filter(F.col("headcount") > 5) \
  .orderBy(F.desc("avg_salary"))

# Both produce the SAME optimized physical plan!
# Catalyst optimizer treats them identically.
✅

SQL vs DataFrame API: Both go through the same Catalyst optimizer and produce identical physical plans. Choose based on team preference. SQL is great for analysts, DataFrame API for engineers.

Joins & Shuffles

⏱ 5 min📌 Module 08🎓 Advanced

Join Types in Spark

# Inner join (default)
df1.join(df2, "customer_id")
df1.join(df2, df1.id == df2.cust_id)

# Left, Right, Full outer
df1.join(df2, "customer_id", "left")
df1.join(df2, "customer_id", "right")
df1.join(df2, "customer_id", "full")

# Anti join (rows in df1 NOT in df2)
df1.join(df2, "customer_id", "left_anti")

# Semi join (rows in df1 that EXIST in df2, but only df1 columns)
df1.join(df2, "customer_id", "left_semi")

Join Strategies

StrategyWhen UsedHow It Works
Broadcast Hash JoinOne table is small (< 10MB default)Small table is broadcast to all executors. No shuffle!
Sort Merge JoinBoth tables are largeSort both sides, then merge. Requires shuffle.
Shuffle Hash JoinMedium + large tablesHash the smaller side after shuffle.

Broadcast Join Hint

from pyspark.sql.functions import broadcast

# Force broadcast (small dimension table)
result = large_df.join(
    broadcast(small_df),
    "key_column"
)

# Check the plan
result.explain(True)
# Look for "BroadcastHashJoin" in the physical plan
⚠️

Shuffle = expensive. Each shuffle writes data to disk and transfers it across the network. Minimize shuffles by: broadcasting small tables, pre-partitioning data, and using bucketing.

Partitioning & Bucketing

⏱ 4 min📌 Module 09🎓 Advanced

Partitioning (File-Level)

# Write with partitioning — creates folder structure
df.write \
    .mode("overwrite") \
    .partitionBy("country", "year") \
    .parquet("output/events")

# Result on disk:
# output/events/country=US/year=2026/part-00000.parquet
# output/events/country=UK/year=2026/part-00000.parquet

# When you filter on partition columns, Spark skips irrelevant folders
# This is called PARTITION PRUNING
spark.read.parquet("output/events") \
    .filter(F.col("country") == "US")  # only reads US folder!

In-Memory Partitioning

# Check current partitions
df.rdd.getNumPartitions()

# Repartition (causes shuffle — use to increase partitions)
df.repartition(200)
df.repartition("customer_id")  # partition by column

# Coalesce (no shuffle — use to DECREASE partitions)
df.coalesce(10)

Bucketing

# Write bucketed table — data is pre-sorted by bucket key
df.write \
    .mode("overwrite") \
    .bucketBy(16, "customer_id") \
    .sortBy("customer_id") \
    .saveAsTable("bucketed_orders")

# When you JOIN two bucketed tables on the same key,
# Spark can do a SHUFFLE-FREE join!  (Sort Merge Bucket Join)

When to Use What

TechniqueBest ForTrade-off
partitionByFiltering on date/region columnsToo many partitions = small file problem
repartitionIncreasing parallelism before a heavy operationFull shuffle
coalesceReducing file count before writeNo shuffle, but can cause uneven partitions
bucketByRepeated joins on the same keyExtra time on write, faster reads/joins

Performance Tuning

⏱ 5 min📌 Module 10🎓 Advanced

Top Performance Tips

1. Use Parquet/ORC

Columnar formats = less I/O. Predicate pushdown and column pruning work automatically.

2. Broadcast Small Tables

If one table is < 100MB, broadcast it to avoid a full shuffle during joins.

3. Tune Shuffle Partitions

Default 200 is too many for small data, too few for huge data. Set to 2-3x your core count.

4. Avoid collect()

collect() pulls ALL data to the driver. Use show(), take(), or write to file instead.

Cache & Persist

# Cache in memory (use when DataFrame is re-used multiple times)
df.cache()            # = persist(StorageLevel.MEMORY_ONLY)
df.persist()          # default: MEMORY_AND_DISK

# Storage levels
from pyspark import StorageLevel
df.persist(StorageLevel.MEMORY_ONLY)        # fastest, spills to recompute
df.persist(StorageLevel.MEMORY_AND_DISK)    # spills to disk
df.persist(StorageLevel.DISK_ONLY)          # all on disk

# Unpersist when done
df.unpersist()

Explain Plan

# See what Spark will actually do
df.explain()          # physical plan
df.explain(True)      # parsed → analyzed → optimized → physical
df.explain("formatted")  # pretty-printed (Spark 3.x)

# What to look for:
# ✅ BroadcastHashJoin (good for small-large joins)
# ⚠  SortMergeJoin    (shuffle — check if broadcast is possible)
# ❌  CartesianProduct  (bug! missing join condition)
# ✅  FileScan with PartitionFilters (partition pruning working)

AQE — Adaptive Query Execution (Spark 3.x)

# Auto-tunes at runtime — enabled by default in Spark 3.x
spark.conf.set("spark.sql.adaptive.enabled", "true")

# What AQE does:
# ✅ Coalesces small post-shuffle partitions
# ✅ Converts Sort Merge Join → Broadcast Join at runtime
# ✅ Optimizes skewed joins (splits hot partitions)

Structured Streaming

⏱ 5 min📌 Module 11🎓 Ecosystem

Structured Streaming treats a live data stream as an unbounded table. You write the same DataFrame/SQL code — Spark handles the incremental processing.

Basic Streaming Pipeline

# Read stream from Kafka
stream_df = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "broker:9092") \
    .option("subscribe", "events") \
    .load()

# Transform (same API as batch!)
parsed = stream_df.select(
    F.from_json(F.col("value").cast("string"), schema).alias("data")
).select("data.*")

# Write stream
query = parsed.writeStream \
    .outputMode("append") \
    .format("parquet") \
    .option("checkpointLocation", "/checkpoint/events") \
    .start("/output/events")

query.awaitTermination()

Output Modes

ModeBehaviorUse Case
appendOnly new rows added to outputETL pipelines, log ingestion
completeEntire result rewritten each triggerAggregation dashboards
updateOnly changed rows writtenReal-time analytics

Watermarking (Late Data)

# Handle late-arriving data with a 10-minute watermark
windowed = parsed \
    .withWatermark("event_time", "10 minutes") \
    .groupBy(F.window("event_time", "5 minutes")) \
    .count()

Delta Lake Basics

⏱ 4 min📌 Module 12🎓 Ecosystem

Delta Lake is an open-source storage layer that brings ACID transactions, schema enforcement, and time travel to data lakes. Built on Parquet.

Key Features

ACID Transactions

Concurrent reads and writes are safe. No corrupted data from failed writes.

Schema Enforcement

Rejects writes that don't match the table schema. Prevents data quality issues.

Time Travel

Query previous versions of your data. Rollback mistakes. Audit changes.

MERGE (Upsert)

Insert, update, or delete in one atomic operation. Essential for CDC and SCD.

Core Operations

# Write as Delta
df.write.format("delta").mode("overwrite").save("/data/events")

# Read Delta
df = spark.read.format("delta").load("/data/events")

# Time Travel — read a previous version
df_v2 = spark.read.format("delta") \
    .option("versionAsOf", 2) \
    .load("/data/events")

# MERGE — upsert pattern
from delta.tables import DeltaTable

target = DeltaTable.forPath(spark, "/data/customers")
target.alias("t").merge(
    updates_df.alias("s"),
    "t.customer_id = s.customer_id"
).whenMatchedUpdateAll() \
 .whenNotMatchedInsertAll() \
 .execute()

# View history
delta_table = DeltaTable.forPath(spark, "/data/events")
delta_table.history().show()

Apache Iceberg

⏱ 5 min📌 Module 13🎓 Ecosystem

Apache Iceberg is an open table format for huge analytic datasets. Like Delta Lake, it brings ACID transactions and time travel to data lakes — but with a different architecture designed for engine-agnostic interoperability (Spark, Trino, Flink, Hive, Dremio, Snowflake, etc.).

Iceberg vs Delta Lake

FeatureDelta LakeApache Iceberg
CreatorDatabricksNetflix → Apache Foundation
Engine SupportBest with Spark/DatabricksEngine-agnostic (Spark, Trino, Flink, Snowflake, etc.)
ACID TransactionsYesYes
Time TravelYesYes (snapshot-based)
Schema EvolutionYesYes (full — add, drop, rename, reorder)
Partition EvolutionNo (must rewrite)Yes — change partition scheme without rewriting data
Hidden PartitioningNoYes — users don't need to know partition layout
CatalogUnity Catalog / HiveHive, AWS Glue, Nessie, REST, JDBC
File FormatParquetParquet, ORC, Avro

Key Iceberg Concepts

Snapshot Isolation

Each write creates a new snapshot. Readers always see a consistent snapshot — no dirty reads, even during writes.

Hidden Partitioning

Partition transforms (year, month, bucket, truncate) are applied automatically. Users query with regular filters — no need to know partition layout.

Partition Evolution

Change the partition scheme without rewriting data. Old data keeps old partitioning; new data uses the new scheme. Both work together.

Metadata Tree

Catalog → Metadata File → Manifest List → Manifest Files → Data Files. Enables efficient file pruning without listing directories.

spark.sql("""
    CREATE TABLE my_catalog.db.events (
        event_id   BIGINT,
        event_type STRING,
        user_id    BIGINT,
        event_time TIMESTAMP,
        payload    STRING
    )
    USING iceberg
    PARTITIONED BY (days(event_time))
""")

# Hidden partitioning transforms:
# years(ts)       → partition by year
# months(ts)      → partition by month
# days(ts)        → partition by day
# hours(ts)       → partition by hour
# bucket(N, col)  → hash into N buckets
# truncate(L, col)→ truncate string/int to length L

Reading & Writing

# Read an Iceberg table
df = spark.read.format("iceberg").load("my_catalog.db.events")
# or
df = spark.table("my_catalog.db.events")

# Write / Append
df.writeTo("my_catalog.db.events").append()
df.writeTo("my_catalog.db.events").overwritePartitions()

# Time Travel — read a specific snapshot
spark.read.format("iceberg") \
    .option("snapshot-id", 123456789) \
    .load("my_catalog.db.events")

# Time Travel — read at a timestamp
spark.read.format("iceberg") \
    .option("as-of-timestamp", "1680000000000") \
    .load("my_catalog.db.events")

MERGE INTO (Upsert)

spark.sql("""
    MERGE INTO my_catalog.db.customers t
    USING updates s
    ON t.customer_id = s.customer_id
    WHEN MATCHED THEN UPDATE SET *
    WHEN NOT MATCHED THEN INSERT *
""")

Schema & Partition Evolution

# Add a column (no rewrite needed)
spark.sql("ALTER TABLE my_catalog.db.events ADD COLUMN region STRING")

# Evolve partition scheme — future writes use new scheme,
# old data keeps old scheme. Both work together!
spark.sql("ALTER TABLE my_catalog.db.events ADD PARTITION FIELD bucket(16, user_id)")

# Table maintenance
spark.sql("CALL my_catalog.system.rewrite_data_files('db.events')")   # compaction
spark.sql("CALL my_catalog.system.expire_snapshots('db.events', TIMESTAMP '2026-01-01')")

Spark skips operations it deems unnecessary
Transformations are not executed until an action is called
Operations run during off-peak hours

filter()
select()

Broadcast Hash Join

They are identical
repartition() causes a shuffle; coalesce() does not
repartition is for RDDs, coalesce is for DataFrames

Combines two tables into a view
Performs upserts — insert, update, or delete in one atomic operation
Merges two different schemas
7. What does partition pruning mean?
Spark skips reading partition folders that don't match the filter
Deleting unused partitions from disk
Reducing the number of partitions
8. What does AQE (Adaptive Query Execution) do?
Automatically caches all DataFrames
Optimizes query plans at runtime based on actual data statistics
Schedules jobs during quiet periods
