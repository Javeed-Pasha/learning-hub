What is SQL?

⏱ 20 min📌 Module 01🎓 Theory

Structured Query Language (SQL) is the standard language for interacting with relational databases. Whether you're a data engineer building pipelines, a data analyst pulling reports, or a backend developer — SQL is the universal skill.

Why SQL Matters

Universal Language

Works across PostgreSQL, MySQL, SQL Server, Oracle, Snowflake, BigQuery, Redshift, and more.

Declarative

You describe what data you want, not how to get it. The optimizer figures out the execution plan.

50+ Years Strong

Created at IBM in the 1970s. Still the #1 language for data. Every modern data tool speaks SQL.

Career Essential

Required for data engineering, analytics, backend development, and data science roles.

How a SQL Query Executes

-- Logical order of operations (NOT the order you write them)

1. FROM       → Identify source tables
2. JOIN       → Combine tables
3. WHERE      → Filter rows
4. GROUP BY   → Aggregate into groups
5. HAVING     → Filter groups
6. SELECT     → Choose columns / expressions
7. DISTINCT   → Remove duplicates
8. ORDER BY   → Sort results
9. LIMIT      → Restrict row count
💡

The logical execution order explains why you can't use a column alias from SELECT inside WHERE — because WHERE runs before SELECT.

Database Fundamentals

⏱ 25 min📌 Module 02🎓 Theory

A relational database stores data in tables (relations) made of rows (records) and columns (fields). Tables are linked via keys.

Key Concepts

Primary Key (PK)

Uniquely identifies each row. Cannot be NULL. Every table should have one. Can be single or composite (multi-column).

Foreign Key (FK)

References a primary key in another table. Enforces referential integrity — prevents orphan records.

Schema

A logical container/namespace for tables, views, and other objects. Helpful for organizing large databases.

Normalization

Process of organizing tables to reduce redundancy. Normal forms: 1NF, 2NF, 3NF, BCNF.

Normalization Quick Reference

1NFAtomic values only — no repeating groups or arraysA column storing tag1,tag2,tag3
2NF1NF + no partial dependencies on composite PKNon-key column depends on only part of a composite key
3NF2NF + no transitive dependenciesColumn depends on another non-key column instead of PK

SELECT & Filtering

⏱ 30 min📌 Module 04🎓 Hands-On

The SELECT statement is the workhorse of SQL. It retrieves data from one or more tables.

Basic SELECT

-- Select specific columns
SELECT name, email, created_at
FROM customers;

-- Select all columns (avoid in production)
SELECT * FROM customers;

-- Aliasing columns
SELECT
  first_name AS "First Name",
  salary * 12 AS annual_salary
FROM employees;

WHERE Clause — Filtering Rows

-- Comparison operators
SELECT * FROM products WHERE price > 100;
SELECT * FROM products WHERE price BETWEEN 50 AND 200;

-- Pattern matching
SELECT * FROM customers WHERE name LIKE 'J%';        -- starts with J
SELECT * FROM customers WHERE name LIKE '__a%';      -- 3rd char is 'a'

-- NULL handling
SELECT * FROM orders WHERE shipped_date IS NULL;
SELECT * FROM orders WHERE shipped_date IS NOT NULL;

-- IN — match from a list
SELECT * FROM orders WHERE status IN ('shipped', 'delivered');

-- AND / OR / NOT
SELECT * FROM products
WHERE category = 'Electronics'
  AND price < 500
  AND stock > 0;

ORDER BY & LIMIT

-- Sort ascending (default) and descending
SELECT * FROM products ORDER BY price DESC;

-- Top N results
SELECT * FROM products ORDER BY price DESC LIMIT 10;

-- Pagination: OFFSET + LIMIT
SELECT * FROM products ORDER BY name LIMIT 20 OFFSET 40;  -- page 3

DISTINCT

-- Unique values
SELECT DISTINCT category FROM products;

-- Count unique values
SELECT COUNT(DISTINCT category) FROM products;
✅

Best Practice: Never use SELECT * in production queries or views. Always list the columns you need — it's faster and more maintainable.

JOINs Deep Dive

⏱ 40 min📌 Module 05🎓 Core Concept

JOINs combine rows from two or more tables based on a related column. This is the heart of relational databases.

JOIN Types Visual

  INNER JOIN         LEFT JOIN          RIGHT JOIN         FULL OUTER JOIN

   ┌───┬───┐          ┌───┬───┐          ┌───┬───┐          ┌───┬───┐
   │   │███│          │███│███│          │   │███│          │███│███│
   │ A │█B█│          │█A█│█B█│          │ A │█B█│          │█A█│█B█│
   │   │███│          │███│███│          │   │███│          │███│███│
   └───┴───┘          └───┴───┘          └───┴───┘          └───┴───┘
  Only matching       All from A +        All from B +       Everything
  rows in both        matching B          matching A         from both

INNER JOIN

-- Only rows with matches in BOTH tables
SELECT
  c.name,
  o.order_id,
  o.total_amount
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id;

LEFT JOIN (LEFT OUTER JOIN)

-- ALL customers, even those with no orders (NULLs for order columns)
SELECT
  c.name,
  o.order_id,
  COALESCE(o.total_amount, 0) AS total
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;

-- Find customers who NEVER ordered (anti-join pattern)
SELECT c.name
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;

CROSS JOIN

-- Cartesian product: every combination of rows
SELECT color, size
FROM colors CROSS JOIN sizes;
-- 3 colors × 4 sizes = 12 rows

SELF JOIN

-- Find employees and their managers
SELECT
  e.name AS employee,
  m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.employee_id;

Multi-Table JOINs

-- Orders with customer names + product details
SELECT
  c.name AS customer,
  o.order_id,
  p.name AS product,
  oi.quantity,
  oi.unit_price
FROM customers c
JOIN orders o       ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id    = oi.order_id
JOIN products p     ON oi.product_id = p.product_id
ORDER BY o.order_id;
⚠️

Watch out for duplicates! If the join creates a one-to-many relationship, aggregation counts will inflate. Always check row counts after joining.

Aggregations & GROUP BY

⏱ 30 min📌 Module 06🎓 Hands-On

Aggregate Functions

FunctionDescriptionExample
COUNT(*)Count all rows (incl. NULLs)COUNT(*)
COUNT(col)Count non-NULL valuesCOUNT(email)
SUM(col)Total of numeric columnSUM(amount)
AVG(col)Average (ignores NULLs)AVG(price)
MIN(col)Smallest valueMIN(created_at)
MAX(col)Largest valueMAX(salary)

GROUP BY

-- Total revenue per customer
SELECT
  c.name,
  COUNT(o.order_id) AS total_orders,
  SUM(o.total_amount) AS total_spent,
  AVG(o.total_amount) AS avg_order_value
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.name
ORDER BY total_spent DESC;

HAVING — Filtering Groups

-- Customers who spent more than $1000
SELECT
  c.name,
  SUM(o.total_amount) AS total_spent
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.name
HAVING SUM(o.total_amount) > 1000
ORDER BY total_spent DESC;
💡

WHERE vs HAVING: WHERE filters individual rows before grouping. HAVING filters groups after aggregation. Use WHERE for row-level conditions and HAVING for aggregate conditions.

Subqueries & CTEs

⏱ 35 min📌 Module 07🎓 Intermediate

Subqueries

-- Scalar subquery: products priced above average
SELECT name, price
FROM products
WHERE price > (SELECT AVG(price) FROM products);

-- IN subquery: customers who placed orders in 2026
SELECT name
FROM customers
WHERE customer_id IN (
  SELECT customer_id FROM orders
  WHERE order_date >= '2026-01-01'
);

-- EXISTS: more efficient than IN for large datasets
SELECT c.name
FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.customer_id
    AND o.total_amount > 500
);

Common Table Expressions (CTEs)

-- CTEs make complex queries readable
WITH monthly_revenue AS (
  SELECT
    DATE_TRUNC('month', order_date) AS month,
    SUM(total_amount) AS revenue
  FROM orders
  GROUP BY 1
),
avg_revenue AS (
  SELECT AVG(revenue) AS avg_rev FROM monthly_revenue
)
SELECT
  mr.month,
  mr.revenue,
  ar.avg_rev,
  CASE WHEN mr.revenue > ar.avg_rev
       THEN 'Above Average'
       ELSE 'Below Average'
  END AS performance
FROM monthly_revenue mr, avg_revenue ar
ORDER BY mr.month;
✅

Prefer CTEs over nested subqueries. CTEs are named, readable, and reusable within the query. They're the standard in modern SQL.

Window Functions

⏱ 40 min📌 Module 08🎓 Advanced

Window functions perform calculations across a set of rows related to the current row — without collapsing rows like GROUP BY does.

Syntax

function_name(...) OVER (
  [PARTITION BY column]     -- divide into groups
  [ORDER BY column]         -- sort within partition
  [ROWS/RANGE frame_spec]   -- define window frame
)

Ranking Functions

SELECT
  name,
  department,
  salary,
  ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn,
  RANK()       OVER (PARTITION BY department ORDER BY salary DESC) AS rnk,
  DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS drnk
FROM employees;
FunctionTies BehaviorGapsExample: salaries 100, 100, 90
ROW_NUMBER()Arbitrary for tiesNo1, 2, 3
RANK()Same rank for tiesYes1, 1, 3
DENSE_RANK()Same rank for tiesNo1, 1, 2

LAG & LEAD

-- Compare each month's revenue with the previous month
SELECT
  month,
  revenue,
  LAG(revenue, 1) OVER (ORDER BY month)  AS prev_month,
  LEAD(revenue, 1) OVER (ORDER BY month) AS next_month,
  revenue - LAG(revenue) OVER (ORDER BY month) AS mom_change
FROM monthly_revenue;

Running Totals & Moving Averages

-- Running total of revenue
SELECT
  order_date,
  total_amount,
  SUM(total_amount) OVER (ORDER BY order_date) AS running_total,
  AVG(total_amount) OVER (
    ORDER BY order_date
    ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
  ) AS moving_avg_7d
FROM orders;
💡

Classic interview pattern: "Get the top N per group" → Use ROW_NUMBER() OVER (PARTITION BY group ORDER BY metric DESC) in a CTE, then filter WHERE rn <= N.

DML — INSERT, UPDATE, DELETE

⏱ 25 min📌 Module 09🎓 Hands-On

INSERT

-- Single row
INSERT INTO customers (name, email)
VALUES ('Alice', 'alice@example.com');

-- Multiple rows
INSERT INTO products (name, price, category)
VALUES
  ('Keyboard', 79.99, 'Electronics'),
  ('Mouse', 49.99, 'Electronics'),
  ('Desk Lamp', 34.99, 'Office');

-- INSERT from SELECT
INSERT INTO archive_orders
SELECT * FROM orders WHERE order_date < '2025-01-01';

UPDATE

-- Update specific rows
UPDATE products
SET price = price * 1.10
WHERE category = 'Electronics';

-- Update with a JOIN (PostgreSQL syntax)
UPDATE orders o
SET status = 'vip'
FROM customers c
WHERE o.customer_id = c.customer_id
  AND c.tier = 'premium';

DELETE

-- Delete specific rows
DELETE FROM orders WHERE status = 'cancelled';

-- TRUNCATE: delete ALL rows (faster, no WHERE allowed)
TRUNCATE TABLE temp_staging;
⚠️

Always add a WHERE clause to UPDATE/DELETE. Without it, you'll modify or delete every row in the table. Run a SELECT first to verify your filter.

DDL & Schema Design

⏱ 30 min📌 Module 10🎓 Intermediate

CREATE TABLE

CREATE TABLE employees (
  employee_id  SERIAL PRIMARY KEY,
  first_name   VARCHAR(50)  NOT NULL,
  last_name    VARCHAR(50)  NOT NULL,
  email        VARCHAR(100) UNIQUE NOT NULL,
  department   VARCHAR(50),
  salary       DECIMAL(10,2) CHECK (salary > 0),
  hire_date    DATE DEFAULT CURRENT_DATE,
  manager_id   INT REFERENCES employees(employee_id),
  created_at   TIMESTAMP DEFAULT NOW()
);

ALTER TABLE

-- Add column
ALTER TABLE employees ADD COLUMN phone VARCHAR(20);

-- Rename column
ALTER TABLE employees RENAME COLUMN phone TO mobile;

-- Change data type
ALTER TABLE employees ALTER COLUMN salary TYPE NUMERIC(12,2);

-- Add constraint
ALTER TABLE orders ADD CONSTRAINT fk_customer
  FOREIGN KEY (customer_id) REFERENCES customers(customer_id);

-- Drop column
ALTER TABLE employees DROP COLUMN mobile;

Views

-- Create a virtual table (saved query)
CREATE VIEW v_customer_summary AS
SELECT
  c.customer_id,
  c.name,
  COUNT(o.order_id) AS total_orders,
  SUM(o.total_amount) AS lifetime_value
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name;

-- Use it like a table
SELECT * FROM v_customer_summary WHERE lifetime_value > 1000;

Indexes & Performance

⏱ 35 min📌 Module 11🎓 Advanced

Indexes are data structures that speed up row lookups at the cost of extra storage and slower writes.

Index Types

B-Tree (Default)

Best for equality and range queries. Used by most columns. =, <, >, BETWEEN, ORDER BY.

Hash

Only for equality (=). Faster than B-Tree for exact matches, but no range support.

GIN

Generalized Inverted Index. Best for full-text search, arrays, JSONB. PostgreSQL-specific.

Composite

Index on multiple columns. Column order matters: leftmost column first for filtering.

Creating Indexes

-- Single column index
CREATE INDEX idx_orders_date ON orders (order_date);

-- Composite index (column order matters!)
CREATE INDEX idx_orders_cust_date ON orders (customer_id, order_date);

-- Unique index
CREATE UNIQUE INDEX idx_users_email ON users (email);

-- Partial index (only index active orders)
CREATE INDEX idx_active_orders ON orders (customer_id)
WHERE status = 'active';

EXPLAIN — Reading Query Plans

EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 42;

-- Key things to look for:
-- ✅ Index Scan  → using an index (fast)
-- ❌ Seq Scan    → full table scan (slow on large tables)
-- ⚠  Sort        → might need an index on ORDER BY column

Performance Tips

Transactions & ACID

⏱ 25 min📌 Module 12🎓 Theory

A transaction is a group of SQL operations that succeed or fail as a unit. They guarantee data consistency.

ACID Properties

Atomicity

All or nothing. Either every statement in the transaction succeeds, or none do. No partial updates.

Consistency

Data moves from one valid state to another. All constraints (PK, FK, CHECK) are enforced.

Isolation

Concurrent transactions don't interfere with each other. Each sees a consistent snapshot of data.

Durability

Once committed, data survives crashes. Written to disk, not just memory.

Transaction Syntax

-- Transfer $100 from account A to account B
BEGIN;

UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
UPDATE accounts SET balance = balance + 100 WHERE id = 'B';

-- If everything OK:
COMMIT;

-- If something went wrong:
ROLLBACK;

Isolation Levels

LevelDirty ReadNon-Repeatable ReadPhantom Read
Read UncommittedPossiblePossiblePossible
Read CommittedNoPossiblePossible
Repeatable ReadNoNoPossible
SerializableNoNoNo
💡

Default level: Most databases use Read Committed. PostgreSQL's Repeatable Read is actually Serializable Snapshot Isolation (SSI).

Quick Cheat Sheet

Query Template

SELECT   column1, AGG(column2)
FROM     table1
JOIN     table2      ON table1.id = table2.fk_id
WHERE    condition    -- row filter (before grouping)
GROUP BY column1
HAVING   AGG(column2) > value  -- group filter
ORDER BY column1 DESC
LIMIT    10;
