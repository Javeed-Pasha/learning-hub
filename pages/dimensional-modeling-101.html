What is Dimensional Modeling?

⏱ 4 min📌 Module 01🎓 Theory

Dimensional modeling is a data warehouse design technique created by Ralph Kimball. It organizes data into facts (measurable events) and dimensions (context/descriptors), optimized for query performance and business understanding.

Why Dimensional Modeling?

Query Performance

Star schemas minimize joins. Aggregation queries run fast because the engine scans a narrow fact table and looks up dimensions.

Business Friendly

Non-technical users can understand "Sales by Product by Region by Month." The model mirrors how the business thinks.

Predictable Patterns

Every query follows the same pattern: pick a fact, filter/group by dimensions. BI tools love this structure.

Industry Standard

Used in virtually every data warehouse — from on-prem (Teradata, Oracle) to cloud (Snowflake, BigQuery, Redshift).

OLTP vs OLAP

AspectOLTP (Operational DB)OLAP (Data Warehouse)
PurposeRun the business (transactions)Analyze the business (reporting)
DesignNormalized (3NF)Denormalized (Star/Snowflake)
QueriesINSERT/UPDATE on single rowsSELECT with aggregations on millions of rows
UsersApplications, developersAnalysts, BI tools, data scientists
Data VolumeCurrent state (GB)Historical (TB–PB)
NormalizationHighly normalizedDenormalized for read performance
💡

The Kimball mantra: "Design for understandability and query performance first, storage cost second." In a data warehouse, denormalization is a feature, not a flaw.

Facts & Dimensions

⏱ 5 min📌 Module 02🎓 Core Concept

Fact Tables

A fact table records business events or measurements — things that happened. Each row is a grain (the most atomic level of detail).

Characteristics

Numeric, additive measures (revenue, quantity, cost). Foreign keys to dimension tables. Narrow and very tall (billions of rows).

Examples

fact_sales, fact_orders, fact_page_views, fact_inventory_snapshot, fact_shipments

Dimension Tables

A dimension table provides the context/descriptors for a fact — the who, what, where, when, how.

Characteristics

Textual, descriptive attributes. Primary key (usually surrogate). Wide and short (thousands to millions of rows).

Examples

dim_customer, dim_product, dim_date, dim_store, dim_employee, dim_promotion

The Grain

The grain defines what one row in the fact table represents. This is the single most important design decision.

Fact TableGrain
fact_salesOne line item on a sales receipt
fact_inventoryDaily snapshot of inventory per product per store
fact_page_viewsOne page view by one user at one timestamp
fact_monthly_revenueMonthly revenue per product category (pre-aggregated)
⚠️

Always declare the grain first. If you can't state in one sentence what a fact row represents, stop and clarify before designing anything else. Mixed grain = broken aggregations.

Star vs Snowflake Schema

⏱ 4 min📌 Module 03🎓 Core Concept

Star Schema

                        ┌──────────────┐
                        │  dim_date    │
                        ├──────────────┤
                        │ date_key  PK │
                        │ full_date    │
                        │ day_of_week  │
                        │ month_name   │
                        │ quarter      │
                        │ year         │
                        └──────┬───────┘
                               │
  ┌──────────────┐    ┌────────┴────────┐    ┌──────────────┐
  │ dim_product  │    │  fact_sales     │    │ dim_store    │
  ├──────────────┤    ├─────────────────┤    ├──────────────┤
  │ product_key PK│◀───│ product_key  FK │    │ store_key PK │
  │ product_name │    │ store_key    FK │───▶│ store_name   │
  │ category     │    │ date_key     FK │    │ city         │
  │ brand        │    │ customer_key FK │    │ state        │
  │ unit_cost    │    │───────────────  │    │ region       │
  └──────────────┘    │ quantity        │    └──────────────┘
                      │ unit_price      │
  ┌──────────────┐    │ discount_amt    │
  │ dim_customer │    │ total_amount    │
  ├──────────────┤    └─────────────────┘
  │ customer_key PK│◀─────────┘
  │ full_name    │
  │ email        │
  │ city         │
  │ segment      │
  └──────────────┘

Snowflake Schema

A snowflake schema normalizes dimension tables into sub-dimensions. For example, dim_product links to dim_category which links to dim_department.

  ┌─────────────┐    ┌─────────────┐    ┌──────────────┐
  │ dim_dept    │◀───│ dim_category│◀───│ dim_product  │
  ├─────────────┤    ├─────────────┤    ├──────────────┤
  │ dept_key  PK│    │ cat_key   PK│    │ product_key PK│─── ▶ fact_sales
  │ dept_name   │    │ cat_name    │    │ product_name │
  └─────────────┘    │ dept_key  FK│    │ brand        │
                     └─────────────┘    │ cat_key    FK│
                                        └──────────────┘

Comparison

AspectStar SchemaSnowflake Schema
JoinsFewer (fact → dim)More (fact → dim → sub-dim)
Query SpeedFaster (fewer joins)Slower (more joins)
StorageMore (denormalized dims)Less (normalized)
ComplexitySimpler to understandMore complex
BI Tool SupportExcellentGood (some tools prefer star)
MaintenanceUpdate in one placeUpdates cascade through sub-dims
✅

Kimball's recommendation: Start with a star schema. Only snowflake when there's a compelling reason (e.g., a very large, frequently-changing dimension hierarchy). Most modern cloud DWs handle denormalized dims easily.

Fact Table Design

⏱ 5 min📌 Module 04🎓 Design

Types of Fact Tables

Transaction Fact

One row per event. Most common. Fine-grained. Examples: sales, clicks, shipments, payments.

Periodic Snapshot

One row per entity per time period. Captures state at regular intervals. Examples: daily balance, monthly inventory.

Accumulating Snapshot

One row per process instance. Updated as the process progresses. Multiple date FKs. Example: order fulfillment pipeline.

Factless Fact

Records events with no numeric measures — just FK relationships. Examples: student attendance, promotion coverage.

Measure Additivity

TypeBehaviorExamples
AdditiveCan SUM across all dimensionsRevenue, quantity, cost, discount amount
Semi-AdditiveCan SUM across some dimensions but NOT timeAccount balance, inventory count, headcount
Non-AdditiveCannot SUM — must AVG, or use ratiosUnit price, percentages, ratios, temperature

Accumulating Snapshot Example

-- Order fulfillment pipeline: one row per order, updated over time

CREATE TABLE fact_order_fulfillment (
  order_key           INT PRIMARY KEY,
  customer_key        INT REFERENCES dim_customer,

  -- Multiple date FKs — one per milestone
  order_date_key      INT REFERENCES dim_date,   -- when ordered
  ship_date_key       INT REFERENCES dim_date,   -- when shipped
  delivery_date_key   INT REFERENCES dim_date,   -- when delivered
  return_date_key     INT REFERENCES dim_date,   -- if returned

  -- Lag measures
  days_to_ship        INT,
  days_to_deliver     INT,
  order_amount        DECIMAL(10,2)
);
💡

Design tip: Store both the raw additive measures (quantity, revenue) and the pre-computed useful measures (discount_amount, net_amount). Avoid storing only percentages — store the numerator and denominator so users can re-aggregate correctly.

Dimension Table Design

⏱ 5 min📌 Module 05🎓 Design

The Date Dimension

Every data warehouse needs a date dimension. It's the most-used dimension and enables rich time-based analysis.

CREATE TABLE dim_date (
  date_key          INT PRIMARY KEY,   -- YYYYMMDD format (20260403)
  full_date         DATE NOT NULL,
  day_of_week       VARCHAR(10),       -- Monday, Tuesday...
  day_of_week_num   INT,               -- 1-7
  day_of_month      INT,               -- 1-31
  day_of_year       INT,               -- 1-366
  week_of_year      INT,
  month_num         INT,               -- 1-12
  month_name        VARCHAR(10),       -- January, February...
  month_short       VARCHAR(3),        -- Jan, Feb...
  quarter           INT,               -- 1-4
  quarter_name      VARCHAR(2),        -- Q1, Q2...
  year              INT,
  fiscal_quarter    INT,
  fiscal_year       INT,
  is_weekend        BOOLEAN,
  is_holiday        BOOLEAN,
  holiday_name      VARCHAR(50)
);

Best Practices

Wide & Denormalized

Flatten hierarchies into the dimension. Keep category, subcategory, department all in dim_product.

Descriptive Attributes

Include human-readable labels, not just codes. Store both status_code and status_description.

Avoid Nulls

Replace NULLs with meaningful defaults: 'Unknown', 'Not Applicable', 'N/A'. NULLs break GROUP BY behavior.

Add a "Unknown" Row

Every dimension should have a row for key = -1 labeled 'Unknown'. Use it when the FK in the fact table is missing.

Dimension Hierarchies

-- Product hierarchy (all in one table — star schema)

  dim_product
  ┌──────────────────────────────────────────────┐
  │ product_key  PK                               │
  │ product_name                                   │
  │ brand                                          │
  │ subcategory      ← level 1                    │
  │ category         ← level 2                    │
  │ department       ← level 3                    │
  └──────────────────────────────────────────────┘

-- Enables drill-down: Department → Category → Subcategory → Product

Surrogate Keys

⏱ 3 min📌 Module 06🎓 Design

A surrogate key is an artificial, system-generated integer key (e.g., auto-increment) used as the primary key of a dimension table, replacing the natural/business key.

Why Surrogate Keys?

ReasonExplanation
SCD supportTrack historical changes — the same business key can have multiple surrogate keys (one per version)
Source independenceDecouple from source system keys. If the source changes IDs, your warehouse is unaffected
PerformanceInteger joins are faster than string joins. Smaller fact table footprint
Handle "Unknown"Assign surrogate key -1 for unknown/missing dimension members
Multi-source integrationTwo source systems may use the same business key for different entities

Surrogate vs Natural Key

-- Natural key: the business identifier from source
customer_id = 'CUST-10042'    -- from ERP system

-- Surrogate key: warehouse-generated integer
customer_key = 58391            -- auto-increment

-- The dimension table stores BOTH:
dim_customer
  customer_key   INT  PK         -- surrogate (join key)
  customer_id    VARCHAR          -- natural (for traceability)
  customer_name  VARCHAR
  ...

-- The fact table uses ONLY the surrogate key:
fact_sales
  customer_key   INT  FK → dim_customer
✅

Always keep the natural key in the dimension table alongside the surrogate key. You need it for ETL lookups and data lineage back to the source system.

SCD — Slowly Changing Dimensions

⏱ 6 min📌 Module 07🎓 Advanced

Dimensions change over time — a customer moves to a new city, a product gets re-categorized. SCDs define how to handle these changes.

SCD Type 0 — Retain Original

Never update

The attribute is fixed forever. Example: original_signup_date, date_of_birth. Set once, never overwrite.

SCD Type 1 — Overwrite

Overwrite the old value

No history kept. Simple but you lose the previous value. Use for corrections (typos, data quality fixes).

-- Customer moved from NYC to LA
-- BEFORE:
│ customer_key │ name  │ city │
│ 101          │ Alice │ NYC  │

-- AFTER (Type 1: just overwrite):
│ customer_key │ name  │ city │
│ 101          │ Alice │ LA   │

-- ⚠ Historical sales still linked to key 101
-- but now show "LA" — history is lost

SCD Type 2 — Add New Row

Track full history

The most powerful SCD. Insert a new row with a new surrogate key. Add effective_date, end_date, and is_current flag.

-- Customer moved from NYC to LA
-- Type 2: add a new row, close the old one

│ customer_key │ customer_id │ name  │ city │ eff_date   │ end_date   │ is_current │
│ 101          │ CUST-42     │ Alice │ NYC  │ 2024-01-15 │ 2026-03-31 │ N          │
│ 438          │ CUST-42     │ Alice │ LA   │ 2026-04-01 │ 9999-12-31 │ Y          │

-- Sales before April 2026 → linked to key 101 (NYC)
-- Sales after April 2026  → linked to key 438 (LA)
-- ✅ Full history preserved!

SCD Type 3 — Add Column

Track limited history (previous + current)

Add a previous_city column. Only stores one level of history. Rarely used in practice.

-- Type 3: store current + previous
│ customer_key │ name  │ current_city │ previous_city │
│ 101          │ Alice │ LA           │ NYC           │

SCD Comparison

TypeHistory?ComplexityWhen to Use
Type 0No changeNoneImmutable attributes
Type 1NoneSimpleCorrections, non-critical attributes
Type 2FullComplexMust track changes over time (most common for reporting)
Type 3Limited (prev only)MediumRare — need "before and after" comparison
Type 6 (hybrid)Full + currentMost complexType 2 + Type 1 + Type 3 combined
💡

In practice: Most teams use Type 1 for non-critical attributes (e.g., phone number) and Type 2 for business-critical attributes (e.g., customer segment, product category) in the same dimension table.

Junk, Degenerate & Role-Playing Dims

⏱ 4 min📌 Module 08🎓 Advanced

Degenerate Dimension

A dimension with no attributes — lives in the fact table

When a dimension key has no meaningful attributes beyond itself, store it directly in the fact table. No separate dim table needed.

-- Order number and Invoice number are degenerate dimensions
-- They identify the transaction but have no extra attributes

fact_sales
  date_key         FK → dim_date
  product_key      FK → dim_product
  customer_key     FK → dim_customer
  order_number     ← degenerate dimension (no dim table)
  invoice_number   ← degenerate dimension (no dim table)
  quantity         ← measure
  amount           ← measure

Junk Dimension

Combine low-cardinality flags into one dimension

Instead of adding many Y/N flag columns to the fact table, create a single "junk" dimension with all combinations.

-- Instead of these flags cluttering the fact table:
--   is_gift, is_rush, is_online, is_loyalty

-- Create dim_order_flags (junk dimension):
│ flag_key │ is_gift │ is_rush │ is_online │ is_loyalty │
│ 1        │ Y       │ N       │ Y         │ N          │
│ 2        │ N       │ N       │ Y         │ Y          │
│ 3        │ Y       │ Y       │ N         │ N          │
│ ...      │ ...     │ ...     │ ...       │ ...        │

-- 2×2×2×2 = 16 possible combinations
-- Fact table just stores one FK: flag_key

Role-Playing Dimension

Same dimension, different roles in the same fact table

A single physical dimension referenced multiple times through different foreign keys. Most common with dim_date.

-- dim_date plays THREE roles in fact_order_fulfillment:

fact_order_fulfillment
  order_date_key     FK → dim_date   ← role: "Order Date"
  ship_date_key      FK → dim_date   ← role: "Ship Date"
  delivery_date_key  FK → dim_date   ← role: "Delivery Date"

-- In SQL, use aliases:
FROM fact_order_fulfillment f
JOIN dim_date order_dt    ON f.order_date_key    = order_dt.date_key
JOIN dim_date ship_dt     ON f.ship_date_key     = ship_dt.date_key
JOIN dim_date deliver_dt  ON f.delivery_date_key = deliver_dt.date_key

Conformed Dimensions

⏱ 3 min📌 Module 09🎓 Advanced

A conformed dimension is a dimension shared across multiple fact tables. It has the same keys, attributes, and meaning everywhere — enabling cross-process analysis.

Why Conformed Dimensions Matter

  fact_sales                        fact_inventory
  ┌────────────────┐                ┌────────────────┐
  │ product_key FK │─┐          ┌──│ product_key FK │
  │ store_key   FK │─┤          ├──│ store_key   FK │
  │ date_key    FK │─┤          ├──│ date_key    FK │
  │ customer_key FK│ │          │  │ quantity_on_hand│
  │ quantity       │ │          │  └────────────────┘
  │ revenue        │ │          │
  └────────────────┘ │          │
                     ▼          ▼
        ┌─────────────────────────────┐
        │    CONFORMED DIMENSIONS      │
        │                             │
        │  dim_product  (shared)      │
        │  dim_store    (shared)      │
        │  dim_date     (shared)      │
        │                             │
        └─────────────────────────────┘

  Because dim_product is conformed, you can write:
  "Show me sales AND inventory for Electronics in Q1"
  — and the numbers are consistent across both fact tables.
✅

The "data warehouse bus": Kimball's approach is to build the DW incrementally — one business process (fact table) at a time — united by conformed dimensions. dim_date, dim_customer, and dim_product are the most commonly conformed.

Kimball vs Inmon

⏱ 3 min📌 Module 10🎓 Theory

Two competing philosophies for designing a data warehouse:

Architecture Comparison

  KIMBALL (Bottom-Up)                   INMON (Top-Down)

  Source → ETL →  Dimensional DW        Source → ETL → 3NF Enterprise DW
                     │                                      │
                     ▼                                      ▼
                  BI Tools                             Data Marts
                                                      (dimensional)
                                                         │
                                                         ▼
                                                      BI Tools
AspectKimball (Bottom-Up)Inmon (Top-Down)
DW DesignDimensional (star/snowflake)3NF (normalized enterprise model)
ApproachBuild one business process at a timeBuild the full enterprise model first
Data MartsDW IS the collection of martsData marts are built from the DW
Speed to ValueFast — deliver one process at a timeSlow — need full model before any reporting
ComplexitySimpler — fewer joinsComplex — fully normalized
RedundancySome (denormalized)Minimal (3NF)
ETL ComplexityModerateHigh (load 3NF first, then build marts)
Best ForBI/reporting focus, agile teamsEnterprise-wide single source of truth
💡

Modern reality: Most modern data warehouses (Snowflake, BigQuery, Databricks) follow a Kimball-style approach with dimensional models. The Inmon vs Kimball debate is less relevant today — many teams use a hybrid: a lightly-modeled staging/raw layer (like Inmon) feeding dimensional models (like Kimball).

Retail Sales Example

⏱ 5 min📌 Module 11🎓 Real-World

Let's design a complete dimensional model for a retail company's sales analysis.

Business Questions

1. What is total revenue by product category by month?
2. Which stores have the highest sales in Q1?
3. How do promotions impact sales volume?
4. What is the average basket size by customer segment?
5. Show year-over-year growth by region.

Complete Star Schema

CREATE TABLE dim_date (
  date_key      INT PRIMARY KEY,  -- 20260403
  full_date     DATE,
  day_name      VARCHAR(10),
  month_name    VARCHAR(10),
  quarter_name  VARCHAR(2),
  year          INT,
  is_weekend    BOOLEAN,
  is_holiday    BOOLEAN
);

CREATE TABLE dim_product (
  product_key   INT PRIMARY KEY,
  product_id    VARCHAR(20),     -- natural key
  product_name  VARCHAR(100),
  brand         VARCHAR(50),
  subcategory   VARCHAR(50),
  category      VARCHAR(50),
  department    VARCHAR(50),
  unit_cost     DECIMAL(10,2),
  unit_price    DECIMAL(10,2),
  eff_date      DATE,
  end_date      DATE,
  is_current    BOOLEAN
);

CREATE TABLE dim_store (
  store_key     INT PRIMARY KEY,
  store_id      VARCHAR(10),
  store_name    VARCHAR(100),
  city          VARCHAR(50),
  state         VARCHAR(50),
  region        VARCHAR(30),
  store_format  VARCHAR(20)      -- Express, Standard, Superstore
);

CREATE TABLE dim_customer (
  customer_key  INT PRIMARY KEY,
  customer_id   VARCHAR(20),
  full_name     VARCHAR(100),
  email         VARCHAR(100),
  city          VARCHAR(50),
  segment       VARCHAR(20),      -- Regular, Silver, Gold, Platinum
  eff_date      DATE,
  end_date      DATE,
  is_current    BOOLEAN
);

CREATE TABLE dim_promotion (
  promotion_key   INT PRIMARY KEY,
  promotion_name  VARCHAR(100),
  discount_type   VARCHAR(20),    -- Percentage, Fixed, BOGO
  discount_value  DECIMAL(5,2),
  start_date      DATE,
  end_date        DATE
);

-- FACT TABLE: grain = one line item per transaction
CREATE TABLE fact_sales (
  date_key        INT  REFERENCES dim_date,
  product_key     INT  REFERENCES dim_product,
  store_key       INT  REFERENCES dim_store,
  customer_key    INT  REFERENCES dim_customer,
  promotion_key   INT  REFERENCES dim_promotion,
  transaction_id  VARCHAR(20),   -- degenerate dimension
  quantity        INT,
  unit_price      DECIMAL(10,2),
  discount_amount DECIMAL(10,2),
  net_amount      DECIMAL(10,2),
  cost_amount     DECIMAL(10,2)
);

Sample Queries

-- Revenue by category by quarter
SELECT
  d.quarter_name,
  d.year,
  p.category,
  SUM(f.net_amount) AS revenue,
  SUM(f.quantity) AS units_sold
FROM fact_sales f
JOIN dim_date d    ON f.date_key = d.date_key
JOIN dim_product p ON f.product_key = p.product_key
GROUP BY d.quarter_name, d.year, p.category
ORDER BY d.year, d.quarter_name;

-- Top 10 stores by revenue this year
SELECT
  s.store_name, s.region,
  SUM(f.net_amount) AS revenue
FROM fact_sales f
JOIN dim_store s ON f.store_key = s.store_key
JOIN dim_date d  ON f.date_key = d.date_key
WHERE d.year = 2026
GROUP BY s.store_name, s.region
ORDER BY revenue DESC
LIMIT 10;

Common Anti-Patterns

⏱ 3 min📌 Module 12🎓 Pitfalls
Anti-PatternWhy It's BadFix
No declared grain Mixed granularity = wrong aggregations (double-counting) Always state the grain in one sentence before building
NULLs in dimension FKs NULL breaks joins — rows silently disappear in INNER JOINs Use surrogate key -1 pointing to "Unknown" row
Storing derived %s instead of raw values Percentages can't be summed across groups Store numerator + denominator; compute % in the query
Smart keys Encoding meaning in the key (e.g., PROD-EL-001) breaks when rules change Use dumb integer surrogate keys + descriptive columns
One Big Table (OBT) Single giant denormalized table is hard to update, has SCD issues, and wastes storage Use proper star schema — facts + dimensions
Too many dimensions in the fact Fact table becomes wide and slow. 20+ FKs is a smell. Use junk dimensions for flags; check if some "dimensions" are really measures
Calendar fields in the fact table Redundant — month, quarter, year belong in dim_date Store only date_key FK in the fact; derive everything from dim_date
Treating everything as SCD Type 2 Explodes dimension size; slows ETL Use Type 2 only for business-critical attributes; Type 1 for the rest
⚠️

The #1 mistake: Starting to build tables before declaring the grain. If you can't say "one row in this fact table represents ___", you're not ready to design.
